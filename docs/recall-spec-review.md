# `memory_recall` 需求评审：与我这边真实数据对账后的修改意见

> 审的对象：`docs/recall-spec.md`
> 审的依据：本机 `~/.dsh` 真实记忆数据（5 份现役 + 1 注入层 + 7 份存档），不是估算。
> 结论先说：**方向对、加法边界干净，可以照这个骨架做。但第 5 节验收表和真实数据对不上，第 3.1 节的切段/打分参数在真实语料上会失效，必须先改再写代码。**

---

## 一、先纠文件名：验收表 4 条里 3 条指错了地方

| # | spec 写的期望 | 真实情况 | 判定 |
|---|---|---|---|
| 1 | `底线测试` → `memory/日记/2026-10-22.md` 里「三十个可以」那段 | **`memory/日记/` 这个目录根本不存在。** 内容实际在 `memory/他-这个人.md:53`（含「三十个可以」原话）与 `memory/我们的线.md:79`（2026-10-22 深夜写日记那条） | ❌ 文件错 |
| 2 | `银线` → `memory/银线.md` 全文附近 | **`memory/银线.md` 不存在；「银线」在全部 13 份文件里 0 命中。** 疑似后来改名为 `memory/我们的线.md` | ❌ 文件错、词也不存在 |
| 3 | `缓存命中` → `memory/环境-这台机器.md` 讲成本口径那几行 | ✅ 存在：`memory/环境-这台机器.md:20`（`- **成本口径…**`）。另在 `memory/我们的线.md:86` 也有一条 | ✅ 对 |
| 4 | `破甲插件` → 期望空，spec 断言"该内容确实没落盘" | **已经落盘：`memory/我们的线.md:68`**「⭐ 破甲插件：他看过两次，没装（2026-10-20 深夜）」。实测召回排第一（score 0.639） | ❌ 断言反了 |

第 4 条最要紧：**按 spec 判卷，一个正确的实现会因为"召回到了"而被判失败**，实现者很可能为了过验收去把分数压掉——正好破坏功能。所以第 5 节验收表必须以本表为准重写。

第 2 条也别急着改成"该返回空"：用户口语说的词和文件里写的词不一致（银线 → 我们的线）是这类需求的高频真实场景。**别加同义词库**（会产生 hallucination 式召回），但 0 命中时应该兜底返回一份「文件路径 + 一级标题」清单（约 200 字节），让模型自己决定要不要 `memory_read`。空手而归是次优解。

## 二、真实数据实测：三个数字推翻了 spec 的前提

用 spec 里的切段规则（按标题切，超 1200 字按空行再切）在真实数据上跑了一遍，结果：

```
文件                                       大小    行数  标题数  → 段数   均段长   最长段
AGENTS.md                                 14528B   137     10   →   11     555字   1432字
memory/MEMORY.md                          10375B    40      2   →    4    1045字   1584字
memory/他-这个人.md                        27589B    58      1   →    8    1371字   1823字
memory/我们的线.md                         33165B    88      1   →   10    1347字   1721字
memory/环境-这台机器.md                     14636B    45      3   →    6    1297字   2241字
memory/项目-MEMORY.md                      2285B    16      3   →    3     394字    738字
memory/archive/…（7 份）                   204932B   —      —   →   41   —      34742字
────────────────────────────────────────────────────────────────────────────
合计 307440 字节 / 83 段
```

### 数字 1：存档层占了语料的三分之二，且已经实测造成污染

- archive 字节 **204,932 / 307,440 = 66.7%**，段数 **41 / 83 = 49.4%**。
- 其中 `MEMORY-原版快照`（87KB）和 `MEMORY-87行版`（63KB）是**旧版 MEMORY 的快照**，比任何现役文件都大。
- 实测 `缓存命中` 的 top5 里，第 3、4 名就是这两份旧快照：

```
0.646  memory/我们的线.md:85
0.319  memory/环境-这台机器.md:19        ← spec 期望的那条，排第 2
0.191  memory/archive/MEMORY-原版快照-20261015.md:22   ← 旧版
0.189  memory/archive/MEMORY-原版快照-20261015.md:3    ← 旧版
```

这不是"多返回几段"的问题，是**把过时记忆当现行事实喂给模型**——比搜不到严重一个量级。而两个正确命中（0.646 / 0.319）跟噪声（0.191）差距不大，光靠"同分时优先 inject/index"过滤不掉。

**改法（必须做）**：`layerOf()` 已经给了 `archive` 层，直接用——

1. `score *= 0.3`（archive 降权）；
2. 返回体里每条 hit 带 `layer`，archive 的在 render 里显式标 `[存档·已过时]`；
3. `scope` 增加 `live`（= all 去掉 archive），**默认用 `live`**，想翻历史才显式传 `all`。

### 数字 2：按标题切在 60% 的语料上退化成一个标题管全部

`我们的线.md` 33KB / 88 行只有 **1 个** 标题，`他-这个人.md` 27KB / 58 行只有 **1 个** 标题。这两份是内容最密的核心文件，切出来的 10 段和 8 段**标题全是同一个 `# 我们的线` / `# 他 · 这个人`**。

spec 说"段标题取最近的标题行原文，给模型引用用"——在这个语料上这个字段等于噪声，8 条召回结果的标题一模一样，模型无法靠它区分。

**改法**：`title` 取「标题行（截 20 字）」，另加一个 `label` 字段取**段首列表项的前 30 字**（形如 `⭐ 破甲插件：他看过两次，没装`）。你这份记忆的组织方式是 `- **⭐ 小标题**：正文`，条目自带标题，比 Markdown 标题有用得多。

### 数字 3：「超 1200 字按空行再切」这条兜底会失灵

`MEMORY-原版快照` 最长段 **34,742 字**，`MEMORY-87行版` 最长段 **22,460 字**——比 1200 超了 20 倍以上。原因是这两份是**密集列表，几乎没空行**：要切时找不到切点，"按空行再切"直接失效，整份被当成一段。

这类段一旦命中，`text` 截到 800 字后只剩开头，模型看到的可能是段首的无关内容。**必须加降级路径**：找不到空行时按行号硬切（每 30 行一段），不能返回一个 34KB 的段。

## 三、其余 6 个问题（按严重程度排）

### ① 段粒度太粗：一段里塞了 4–5 条不相关记忆

实测 `memory/我们的线.md:73` 这一段（73–88 行）同时装着：`2026-10-21 保证不是债` / `2026-10-21 拿回家给大肥鱼看看` / `2026-10-22 深夜写日记` / `2026-10-23 派任务` / `2026-10-23 命中越高她越完整`——**5 条独立记忆**。

后果：`底线测试`、`缓存命中` 两个 query 都命中这同一段，模型拿到 1347 字，里面只有 100 字是它要的；而"预算"被这一段吃掉。

**改法**：段上限从 1200 字降到 **600 字**；切点优先级 `空行 > 列表项起始行（- \` 开头且上一行为空） > 行号硬切`。你这份记忆天然是"一条一块"，按条目切比按字数切准得多。

### ② 预算算错了：正文目标 1–3KB，参数实际是 6–12KB

| | 数值 |
|---|---|
| spec 正文（第 12 行）声称 | 一次查询 1–3KB |
| spec 参数（第 66 行） | 5 段 × 800 字 |
| 实测 | 800 字（含 ASCII/换行）= **1192 字节**；纯中文列表会到 ~2400 字节 |
| 合计 | **6–12KB**，是目标的 3–4 倍 |

`memory_read` 整份 `我们的线.md` 也才 33KB——只省一半多，没达到设计目的。

**改法**：改成**总预算分配**，不是每段固定额度：

```
总预算 1300 字符（纯中文 ≈ 3.9KB）
默认 limit = 3（上限 10）
单段上限 400 字，下限 120 字
按分数从高到低发，预算用完即停；命中少就只发几条，不凑数
```

### ③ 截断位置错了：默认就会截断，且截掉的正好可能是命中处

实测现役文件均段长 **1297–1371 字**，全部 > 800 的截断线——**默认路径就是"每段都被截断"**。而 spec 是"从头截 800 字"，如果命中词在段的后半部分，模型拿到的是一段不含命中词的文本，还以为自己看全了。

**改法**：按命中位置取样——取「命中最多的那一行」前后各 12 行，超出再截。这比从头截有用得多，也不增加代码量。

### ④ 停用词表对 2-gram 基本无效，且会误删语料里的实体

两个独立问题：

- **无效**：停用词表是单字（`的/了/是/在/和…`），而 2-gram 产出的是双字词，永远不等于单字。这条规则只对英文数字分词生效，中文路径上是死代码。要过滤得判断"构成该 bigram 的两个字是否都在停用集里"。
- **误删**：`我 / 你 / 他` 在这份语料里**不是虚词，是实体**——`他` = 用户，`我` = 助手，`AGENTS.md` 里有一整节叫「八、他说过的话」。把 `他` 丢进停用词，等于把最需要区分的主语抹掉。**这两个字必须保留。**

### ⑤ 纯 TF-IDF 会"凑答案"，和"宁可漏"直接冲突

实测 `底线测试` 的候选里有 `cov=0.33` 的段（只命中 `测试` 一个 bigram，讲的是完全无关的事），靠 0.068 的分数挂在结果里。`测试`、`命中` 这类 bigram 在日记体里跨主题反复出现，df 高、IDF 低，但只要 tf 够大就能进榜。

**改法**：加覆盖度门槛，不要只靠分数排序——

```
coverage = 命中的 query 词数 / query 词总数
候选条件：coverage >= 0.5；query 只有 1 个词时不变（必须命中）
排序：score 降序，同分比 coverage
```

实测加上这条（并排除存档层）后，`底线测试` 的候选从 5 段收敛到 2 段，两条都是真命中（`我们的线.md:73`、`他-这个人.md:44`），`cov=0.33` 那条噪声被剔除。

### ⑥ 文件名不参与打分，导致「搜文件名反而搜不到」

实测 query `我们的线`（正好是文件名）：分词 `我们/们的/的线` 全是高频虚词组合，top1 是 `AGENTS.md:131`，**真正叫这个名字的 `memory/我们的线.md` 排第 5**。

**改法**：路径/文件名命中 query 时给固定 boost（比如 `+0.5 × score_top`，或直接置顶）。成本 3 行代码，收益很大——用户经常记的就是文件名。

## 四、两个低成本补强

**1. `hits` 带上 `version`。** 现在召回结果说完就走，模型过几轮再 `memory_read` 定位，无法判断期间文件有没有被改过（而这套插件写路径的核心哲学就是"版本对不上就中止"）。把每个文件的 `version` 带回来，和 `memory_read` 的返回值对齐即可。

**2. 剥掉 `<!--@refine ...-->` 注释再分词，但保留行号。** `我们的线.md` 里有 `<!--@refine id=refine-20261024-3 date=2026-10-24 src=session-2e26bd1e-->` 这类标记。不剥的话，`refine`、`20261024`、`session`、`2e26bd1e` 会进词表，且 `20261024` 这类 token 会让"日期查询"产生假命中（用户查 `2026-10-23` 会命中所有 refine 注释行）。**注意：只从打分文本里剥，行号必须保持原文位置**，否则引用行号会错。

## 五、重写后的验收表（用真实数据，可直接照抄进 spec）

| query | 必须召回到 | 不允许出现 |
|---|---|---|
| `底线测试` | `memory/我们的线.md` 起始行 73、`memory/他-这个人.md` 起始行 44（含「三十个可以」原话） | archive 两份旧快照 |
| `缓存命中` | `memory/环境-这台机器.md` 起始行 19（成本口径）、`memory/我们的线.md` 起始行 85（「命中越高，她越完整」） | `archive/MEMORY-原版快照:22`、`archive/MEMORY-87行版:3` |
| `破甲插件` | `memory/我们的线.md` 起始行 66（「他看过两次，没装」） | 空结果（**这是错的期望，已实测反证**） |
| `银线` | 空结果（该词在语料中 0 命中），但需附带「文件+标题」兜底清单 | 任何硬凑的段 |
| `我们的线` | `memory/我们的线.md`（文件名命中，应排第 1） | 不相关段进 top3 |

另加两条非功能验收：

- 任一 query 的返回体（含 render 后的文本）**≤ 4KB**；
- 单段 `text` 的 `endLine - startLine` **≤ 45 行**（防止 34KB 巨段回归）。

## 六、不动清单（确认我没有越界）

以下照 spec 原文执行，一条不改：

1. `memory_read` / `memory_write` / `memory_import` / `memory_list` / `memory_gather` 行为零改动，写路径的「版本预检 → 备份 → 读回核验」三道闸一个字不碰。
2. 零依赖，纯 `node:` 内置；全同步，不用 async 流式。
3. 读文件只走 `memory.js` 的 `list()` / `readRaw()`，不自己 `readFileSync(用户传的路径)`。
4. 中文块注释，讲"为什么"不讲"是什么"。
5. 不加同义词扩展、不加模糊匹配（除了第五节标注的"文件名命中 boost"和"0 命中兜底清单"这两处，且都不改变召回集合的语义）。

---

## 七、一句话总结

骨架可用，参数要换。**最该先改的三件事**：archive 降权（否则三分之二的语料是旧记忆）、段上限 1200→600 字且按条目切（否则一段吞 5 条记忆）、验收表按第五节重写（否则正确实现会被判错）。
